# S5 automation runbook

An authorized faculty, librarian or administrator can save a topic via `POST /api/research/intelligence/monitors`; it starts disabled. The same owner explicitly activates it with `PATCH /api/research/intelligence/monitors/<id>` and `{"enabled": true}`. Students cannot create or activate monitors. An operator may then invoke `python -m scripts.ops.research_monitor <monitor-id>` from a persistent research service. No timer is installed or enabled by this change.

The worker claims a ten-minute lease, re-fetches official metadata, compares stable paper IDs and provider-attributed citation observations, saves a new run only when changed, and writes in-app update events. An unchanged second run is idempotent in the unit test. All-provider failure retains the previous run and records an error. Publication date and retrieval timestamp are both kept; `discovered_at` is retrieval time, not publication time.

For the private Postgres adapter, apply `supabase/migrations/20261112000000_s5_durable_research.sql` to the **verified Archipelago** project and provide a server-only transaction-pooler URL as `ARCHIPELAGO_RESEARCH_DATABASE_URL`. Never put that URL in the browser or commit it. The dedicated operator entry point is `python -m scripts.ops.run_s5_scheduler`; it processes at most four due enabled monitors per pass with atomic claims. `GET /api/research/intelligence/monitors/<id>/history` and `GET /api/research/intelligence/updates` are owner scoped. `POST /api/research/intelligence/monitors/<id>/run` is an explicitly authorized manual refresh. No S5 production cron has been enabled. A persistent worker schedule, real Postgres lease-recovery test, and notification delivery proof are still required before activation.
